## Objective

Close the observable Sprint 4 Trip/Parcel integration gaps, prove the full Trip lifecycle with three parcels, and prove that the Notification NestJS consumer receives the new Trip/Parcel notification facts. The existing repository already contains the Day 21 lifecycle runner, Parcel lifecycle handlers, Trip cargo counters, and most Parcel Notification bindings; Day 29 adds the missing public assistant load seam, canonical `trip.cargo.threshold_crossed` and Parcel auto-rejection event payloads, the remaining Notification consumer coverage, and one isolated end-to-end regression. The E2E provisions an isolated operator-owned Trip graph as a test fixture and exercises every lifecycle mutation through Gateway; Day 29 does not add a public/manual Trip-create endpoint.

## Success criteria (DoD — binary, verifiable)

- [ ] An isolated Gateway-level scenario proves: an operator-owned Trip fixture exists, the assigned assistant loads exactly three `PENDING` parcels, the assigned driver starts the `BOARDING` Trip, all three parcels become `IN_TRANSIT`, arrival at the selected drop-off stop enables exactly one parcel to unload, and assigned crew completes the Trip.
- [ ] The scenario proves `parcel.parcel.loaded`, `trip.trip.started`, `parcel.parcel.unloaded`, and `trip.cargo.threshold_crossed` travel through Outbox/RabbitMQ and reach their intended consumers without duplicate Notification rows.
- [ ] Notification has focused evidence for every Sprint 4 notification-facing routing key: `trip.trip.boarding_started`, `trip.cargo.threshold_crossed`, `parcel.parcel.created`, `parcel.parcel.loaded`, `parcel.parcel.unloaded`, `parcel.parcel.review_requested`, and `parcel.parcel.auto_rejected`.
- [ ] Known Sprint 4 integration gaps found during discovery are closed: the public assistant load action exists and enforces assigned-assistant/tenant/idempotency rules; `trip.cargo.threshold_crossed` has its exact registered payload and operator recipient identity; no public/manual Trip-create contract is added.
- [ ] The cross-service failure window is closed by the existing retry protocol: Trip cargo success followed by Parcel commit failure can be retried with the same public idempotency key and converges to one Trip cargo ledger/counter mutation plus one Parcel transition/stats/Outbox commit.

## Contract changes

Task 29.1 registers `POST /v1/assistant/parcels/{parcelId}/load` and `trip.cargo.threshold_crossed` in `VietRide_API_Contract_v1.md` and BSOT §7.3/§13. The load action requires a UUID-v4 `Idempotency-Key`, body `{ tripId: uuid, parcelCode: string }`, authenticated `ASSISTANT` identity/operator derived from JWT, and response data `{ parcelId, parcelCode, status: "LOADED" }`; assigned-crew/tenant mismatch is `403 FORBIDDEN`, hidden Trip/code mismatch is `404 PARCEL_NOT_FOUND`, and invalid state/race is `409 INVALID_STATUS`. The cargo event exact payload is `{ eventId, occurredAt, tripId, operatorId, loadedWeightKg, maxCargoWeightKg, percentFull }`, with `eventId == OutboxEvent.id == RabbitMQ MessageId`; producer, consumer, and registry migrate atomically from `trip.cargo_near_full`. Task 29.1 also reconciles the existing `parcel.parcel.loaded` registry row with its direct `userIds[]` recipients and makes every `parcel.parcel.auto_rejected` producer carry the sender identity required by technical context. No DB migration or new Notification enum is expected because `CARGO_NEAR_FULL_ALERT`, `PARCEL_LOADED`, and `PARCEL_IN_TRANSIT` already exist in canonical Notification DDL. The Day-29 E2E uses an isolated operator-owned Trip graph fixture and does not introduce a public/manual Trip-create endpoint.
