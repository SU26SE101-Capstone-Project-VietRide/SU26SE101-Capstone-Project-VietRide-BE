# Day 22 — Trip edit snapshot + Pricing rules

- **Timeline ref**: `BE_TIMELINE_VU.md` → Day 22 — Trip edit snapshot + Pricing rules (Jira: not listed)
- **Prior checklist**: `docs/handoff/day-21-checklist.md`
- **Plan status**: APPROVED — PLAN-REVIEW passed with no findings; the three Task-22.0 review adjustments are human-confirmed and incorporated

## Objective

Ship operator Trip editing and DriverSchedule cascade without repricing an existing Booking or leaving cross-service state inconsistent. Resolve future-dated stop fares from one Booking-start clock, distinguish manual Trip overrides from obsolete generated template snapshots, and enforce non-overlapping template windows at the database boundary. Publish transactional Trip facts, let Booking own passenger-impact state and passenger notifications for the Day-22 vehicle/schedule/cancellation flows, and preserve the existing Day-21 lifecycle/idempotency and route-change registry behavior. Day 23 remains responsible for passenger accept/reject and timeout/refund resolution.

## Success criteria (DoD — binary, verifiable)

- [ ] `OPERATOR_ADMIN` can PATCH only `baseFare`, `notes`, `vehicleId`, and `routeId` with UUID-v4 idempotency and the approved field-aware lifecycle matrix; a real change returns `200 ApiResponse<TripDetailDto>`, while same-value input is a no-op without audit/event.
- [ ] A Booking captures `pricingAt` exactly once at handler start; fare precedence is `MANUAL_OVERRIDE` → active `RouteStopFareTemplate` → `Trip.baseFare`, and `PaymentSucceeded` never re-queries or changes persisted Booking money.
- [ ] Existing Bookings retain their original `baseFare`, `discountAmount`, and `totalAmount`; cancellation/refund uses the original persisted `totalAmount` after a Trip fare edit.
- [ ] Route changes reject any `PENDING_PAYMENT`/`CONFIRMED` Booking impact and any local HELD/BOOKED seat race; otherwise they atomically rebuild Trip stops/fares/ETA and audit the change.
- [ ] Vehicle swap preserves matching HELD/BOOKED seats, rejects removed/incompatible HELD seats, rejects every incompatible BOARDING swap, and creates Booking-owned `PENDING_SEAT_ASSIGNMENT` only for a SCHEDULED removed-BOOKED impact whose `deadline = min(now + 4h, departureDateTime - 30m)` is strictly greater than `now`.
- [ ] Full DriverSchedule PATCH requires explicit `applyTo`; `FUTURE_ONLY` leaves generated Trips unchanged, while `ALL_PENDING` preflights every affected Trip and commits the schedule, cascades, audits, and Outbox rows all-or-nothing.
- [ ] A day-of-week removal completes the narrow `trip.trip.cancelled` → Booking cancellation → existing `booking.booking.cancelled` → Payment refund pipeline: `PENDING_PAYMENT` cancels with `refundAmount=0`, while `CONFIRMED` cancels with a 100% refund of immutable persisted `totalAmount`; it never leaves Trip cancelled while active Booking/Payment state is untouched.
- [ ] Trip, Booking, Payment, Notification, shared contracts, and Gateway verification pass, including Day-21 lifecycle regression.

## Contract changes

- Add canonical `PATCH /v1/operator/trips/{tripId}`: `OPERATOR_ADMIN`, UUID-v4 `Idempotency-Key`, `200 ApiResponse<TripDetailDto>`, body only `{baseFare?,notes?,vehicleId?,routeId?}`. Omitted means unchanged; `notes:null` clears; null for other fields, empty bodies, and unknown-only bodies are `422 VALIDATION_ERROR`. `departureDateTime` is not a Trip PATCH field and may change on Day 22 only through the approved DriverSchedule `ALL_PENDING` cascade; crew is also excluded from Trip PATCH.
- Trip edit lifecycle: `baseFare`/`routeId` only `SCHEDULED`; `vehicleId` `SCHEDULED|BOARDING` subject to swap rules; `notes` any non-terminal state. A route edit with any `PENDING_PAYMENT` or `CONFIRMED` Booking impact returns exactly `409 TRIP_ROUTE_CHANGE_BOOKINGS_EXIST`. Capture `now` once for swap preflight and `occurredAt`. Same-number enabled equal-or-higher-rank HELD/BOOKED seats remain; absent/disabled/downgraded seats follow the matrix below. An incompatible HELD seat rejects atomically with `409 TRIP_VEHICLE_SWAP_HELD_SEAT_CONFLICT`. An incompatible BOOKED seat may proceed only for a `SCHEDULED` Trip when `deadline = min(now + 4h, departureDateTime - 30m)` is strictly greater than `now`; otherwise return `409 TRIP_VEHICLE_SWAP_TOO_LATE`. Every incompatible `BOARDING` swap returns `409 TRIP_VEHICLE_SWAP_TOO_LATE`.
- Add raw Internal-JWT `GET /internal/v1/bookings/trips/{tripId}/edit-impact?operatorId={operatorId}` → `{tripId,activeBookingCount,activeBookings:[{bookingId,status,seatNumbers}]}` where the required trusted `operatorId` is passed by Trip and every repository query predicates both `trip_id = tripId` and `operator_id = operatorId`; active is `PENDING_PAYMENT|CONFIRMED`, empty is `200`, and no PII is returned.
- Extend existing raw `GET /internal/v1/trips/{tripId}` with optional query `pricingAt`; serialized response fields remain unchanged. When `pricingAt` is present, Trip resolves Booking pricing with `MANUAL_OVERRIDE` → active template (`effectiveFrom <= pricingAt < effectiveUntil`, or open-ended) → `Trip.baseFare`. Persisted legacy `TEMPLATE_SNAPSHOT` rows are readable for legacy/history but non-authoritative in this explicit-pricing branch. When `pricingAt` is omitted, the endpoint preserves its legacy operational snapshot semantics (`MANUAL_OVERRIDE`/persisted `TEMPLATE_SNAPSHOT` when present, otherwise `Trip.baseFare`) and does not consult time-window templates; this keeps existing Parcel, Notification, and non-pricing Booking callers source/wire compatible. Only new Booking creation/round-trip pricing paths must pass one explicit handler-start `pricingAt`.
- Persist `trips.notes VARCHAR(2000) NULL`; trim and normalize blank to null. Add `TripStopFare.source` / `trip_stop_fares.source` with values `TEMPLATE_SNAPSHOT|MANUAL_OVERRIDE`; existing rows backfill `TEMPLATE_SNAPSHOT`. Day 22 stops generating new `TEMPLATE_SNAPSHOT` rows; legacy snapshots remain readable/non-authoritative, and only an explicit per-Trip fare override creates a new `MANUAL_OVERRIDE` row.
- Audit real changes only: Trip actions `TRIP_EDITED`, `TRIP_VEHICLE_SWAPPED`, `TRIP_ROUTE_CHANGED`, `DRIVER_SCHEDULE_CASCADE_APPLIED`; schedule action `DRIVER_SCHEDULE_EDITED` in new append-only `driver_schedule_audit_logs`. Metadata is `{changedFields,before,after,requestId}` and never contains raw idempotency keys.
- Enable PostgreSQL `btree_gist` explicitly in the Trip database. Protect `route_stop_fare_templates` with a concurrency-safe exclusion constraint on UUID `route_id`/`stop_id` equality plus half-open `tstzrange(effective_from,coalesce(effective_until,'infinity'),'[)')` overlap.
- Register fact `trip.trip.vehicle_swapped` with exact payload `{eventId,occurredAt,tripId,operatorId,oldVehicleId,newVehicleId,oldVehiclePlateNumber,newVehiclePlateNumber,departureDateTime,driverUserId,assistantUserId,seatImpacts:[{bookingId,seatNumbers,reason}]}`. `assistantUserId` is nullable but always present. The only `seatImpacts[].reason` values are `SEAT_REMOVED`, `SEAT_DISABLED`, and `SEAT_TYPE_DOWNGRADED`; no extra or renamed seat-impact fields are allowed. Trip notifies crew from this fact.
- Freeze `trip.trip.schedule_changed` as `{eventId,occurredAt,tripId,operatorId,oldDeparture,newDeparture,severity}` and `trip.trip.cancelled` as `{eventId,occurredAt,tripId,operatorId,cancelledAt,cancelReason}`. `severity` is exactly `MINOR|MEDIUM|MAJOR`; Day-22 schedule day removal uses `cancelReason=DRIVER_SCHEDULE_DAY_REMOVED` and `cancelledAt=occurredAt`, while retaining both timestamps for their distinct domain/event meanings. For the Day-22 vehicle/schedule/cancellation flows only, Booking owns passenger-impact state and passenger notifications: Booking consumes both facts, Parcel also consumes cancellation, and Payment/Notification do not consume `trip.trip.cancelled` directly. Payment refunds only from existing `booking.booking.cancelled`; Notification informs passengers in these Day-22 flows only from Booking-owned facts. Existing route-change registry/consumer behavior is unchanged.
- Booking publishes exactly four Day-22 passenger facts. `booking.booking.seat_reassignment_required` carries common `{eventId,occurredAt,bookingId,tripId,userId,pendingActionId,deadline}` plus `{seatNumbers,reason}`. For `CONFIRMED` Bookings only, a MINOR schedule change publishes separate `booking.booking.schedule_change_informational` with exact `{eventId,occurredAt,bookingId,tripId,userId,oldDeparture,newDeparture,severity}` where `severity` is exactly `MINOR`; it has no `pendingActionId` or `deadline`, while MEDIUM/MAJOR alone use `booking.booking.schedule_change_required` with mandatory common pending-action fields plus `{oldDeparture,newDeparture,severity}`. Non-`CONFIRMED` Bookings publish neither schedule informational nor schedule required facts. `booking.booking.pending_action_realerted` carries the common fields plus pending-action `reason=PENDING_SEAT_ASSIGNMENT` and exact seat detail `{seatNumbers,seatImpactReason}`, or `reason=SCHEDULE_CHANGE` and exact MEDIUM/MAJOR schedule detail. Booking commits state before Outbox publication; Notification consumes all four Booking-owned Day-22 facts field-for-field and never consumes `trip.trip.schedule_changed` directly.
- Booking uses its own PostgreSQL-backed Hangfire storage/queue/host for the T+2h pending-action re-alert. Adding `Hangfire.AspNetCore` and `Hangfire.PostgreSql` at centrally pinned versions is approved. Scheduling dedupe is logical by `pendingActionId`; retry/redelivery may create multiple physical Hangfire jobs. Every execution locks and rechecks action existence, unresolved state, and deadline, then uses a deterministic re-alert Outbox event identity derived from `pendingActionId`; only one Outbox side effect can persist and physical duplicates no-op. Preserve DB commit → ensure schedule → Rabbit ACK and broker/DLQ redelivery repair. No new package beyond the approved pair, table, column, migration, `realerted_at`, or custom poller.
- Canonical full `PATCH /v1/operator/driver-schedules/{scheduleId}?applyTo=FUTURE_ONLY|ALL_PENDING` uses `driverUserId`/`assistantUserId`; missing/invalid `applyTo` is `422`. `assistantUserId:null` clears. Existing `/crew` remains a one-release deprecated alias mapped to the same use case with `ALL_PENDING` and UUID-v4 idempotency; cross-path key reuse mismatches because the fingerprint includes method/path/query/body/sub.
- Feasible request precedence, preserving the Day-21 shared middleware, is authentication (`401`) → `OPERATOR_ADMIN` authorization (`403`) → shared pre-reservation checks (required well-formed route match, UUID-v4 key, and body-presence policy) → normalized fingerprint reservation/replay/mismatch/pending → MVC JSON binding plus endpoint query/body validation (`422`) → one handler-start `now` capture for a newly reserved request → domain validation/preflight → one local transaction/commit → replay-store the exact status/body for every reserved response below `500`. Therefore a reserved `422` from missing/invalid `applyTo`, malformed JSON, unknown/empty body, or FluentValidation is replayable; reuse of an already-reserved key with a different query/body/path/subject returns `IDEMPOTENCY_KEY_MISMATCH` before MVC validation. Authentication/authorization and a malformed UUID-v4 key are never cached; `5xx` releases the reservation. No MVC-before-middleware mechanism is claimed or introduced.
- Trip PATCH domain order is fixed: tenant-scoped Trip load/masked `404` → normalize input and compute actual `changedFields` → same-value no-op `200` → lifecycle matrix for changed fields → tenant-scoped Route/Vehicle validation → one Booking impact call when route/vehicle changes → conflict precedence `TRIP_ROUTE_CHANGE_BOOKINGS_EXIST` before `TRIP_VEHICLE_SWAP_HELD_SEAT_CONFLICT` before `TRIP_VEHICLE_SWAP_TOO_LATE`, followed by remaining local route/layout conflicts → only then open a transaction → deterministic lock/reload/revalidate → apply the whole mutation → stage audit/Outbox → one save/commit. No database transaction spans an HTTP call.
- DriverSchedule PATCH body is exactly `{departureTime?,dayOfWeek?,driverUserId?,assistantUserId?,vehicleId?,validUntil?,isActive?}`; `routeId` and `validFrom` are not editable. Omitted means unchanged. Explicit null clears only `assistantUserId`, `vehicleId`, or `validUntil`; explicit null for `departureTime`, `dayOfWeek`, `driverUserId`, or `isActive`, plus empty/unknown-only bodies, is `422 VALIDATION_ERROR`. `validUntil:null` restores an open-ended window. For `vehicleId:null`, `FUTURE_ONLY` clears only the schedule vehicle, preserves every generated Trip, and stops new Trip generation until a vehicle is assigned; each attempted date uses the existing `TripGenerationSkipLog` with reason `OTHER` and a message identifying that no vehicle is assigned—no new enum/schema. `ALL_PENDING` with `vehicleId:null` returns `422 VALIDATION_ERROR` before mutation because `trips.vehicle_id` is NOT NULL; partial or silent application is forbidden.
- DriverSchedule PATCH domain order is fixed: tenant-scoped schedule load/masked `404` → normalize and compute actual changes → same-value no-op `200` → local scalar/window rules (including the `vehicleId:null`/applyTo rule) → tenant/Identity logical-reference validation → schedule/vehicle/crew overlap validation → branch by `applyTo`. `FUTURE_ONLY` updates the schedule and, if active with a vehicle, generates only uncovered future dates without touching any generated Trip; with a null vehicle it records `OTHER` skip logs until assignment. `ALL_PENDING` deterministically enumerates `SCHEDULED|BOARDING` Trips and fetches every Booking projection before any write/transaction. If any affected Trip with a CONFIRMED Booking has `departureDateTime - now < 2h`, the entire edit returns `409 DRIVER_SCHEDULE_EDIT_TOO_LATE` before seat-cascade mutation. Because `routeId` is not editable, `TRIP_ROUTE_CHANGE_BOOKINGS_EXIST` is not part of DriverSchedule precedence. Vehicle cascade uses only `TRIP_VEHICLE_SWAP_HELD_SEAT_CONFLICT` then `TRIP_VEHICLE_SWAP_TOO_LATE`, followed by remaining local conflicts. It then opens one transaction, locks/reloads/revalidates deterministically, applies schedule plus all Trip cascades, stages audits/Outbox, and saves/commits once; any Trip failure rolls back the batch. Removing a `dayOfWeek` cancels no-longer-matching pending Trips. In contrast, shortening `validUntil` or setting `isActive=false` only stops future generation and never cancels or mutates an already generated Trip, for either apply mode; `validUntil:null`/reactivation may generate uncovered future dates only. `/crew` maps to this same command with `ALL_PENDING`.
- Synchronize only the canonical comment for `trip_stops.estimated_arrival_time`: it remains a static planned baseline; an approved pre-departure Route edit or DriverSchedule `ALL_PENDING` cascade may recompute it, while GPS/Tracking dynamic ETA never updates this column. - Vehicle-swap compatibility is keyed by normalized `seatNumber` and uses exactly `STANDARD < SLEEPER_UPPER < SLEEPER_LOWER < VIP`; this rank is only for vehicle-swap compatibility and never affects pricing. `DRIVER_AREA` is not a passenger seat. For `SCHEDULED`, any incompatible HELD seat blocks atomically with `TRIP_VEHICLE_SWAP_HELD_SEAT_CONFLICT`; an incompatible BOOKED seat may create `PENDING_SEAT_ASSIGNMENT` only when the approved strict deadline is viable, otherwise `TRIP_VEHICLE_SWAP_TOO_LATE`. For `BOARDING`, any incompatible HELD or BOOKED seat blocks with `TRIP_VEHICLE_SWAP_TOO_LATE`. AVAILABLE seats may be deterministically removed/replaced; new enabled non-`DRIVER_AREA` passenger seats become AVAILABLE, while disabled/`DRIVER_AREA` entries never become passenger TripSeats.
- Extend the shared fingerprint from method/route/route-values/subject/body to method/normalized-route/normalized-route-values/normalized-query/subject/canonical-body. Query keys sort ordinally; absent and empty remain distinct; decoded ASP.NET request values are used; repeated-value order is preserved; no query parameter is omitted.
