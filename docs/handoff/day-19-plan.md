## Objective
Day 19 delivers a read-only, tenant-scoped operator booking monitor: a paged/filterable booking list and a booking detail view with lifecycle timeline. Every Booking SQL query must constrain `operator_id` from the authenticated JWT claim, never from client input. Both `OPERATOR_ADMIN` and `OPERATOR_STAFF` may use the endpoints. Passenger-phone filtering resolves an exact normalized phone through an Internal-JWT Identity lookup that returns only `userId`; lifecycle data comes from a new append-only `booking_status_history` table. Task 19.0 records this confirmed contract in the SOT before implementation workers run.

## Success criteria (DoD — binary, verifiable)
- [ ] `GET /v1/operator/bookings?status=&tripId=&date=&page=` returns a paged list containing only bookings whose `operator_id` equals the caller's JWT `operatorId`; a different operator cannot read them. (BE_TIMELINE_VU.md Day 19; BSOT §6.10 tenant isolation)
- [ ] The list accepts dedicated `status` (single/CSV), `tripId`, `date`, `passengerPhone`, and `bookingCode` filters; date means the `Asia/Ho_Chi_Minh` calendar day of `trip_snapshot_departure`, phone is exact after existing normalization, and bookingCode is trimmed exact case-insensitive. All SQL is parameterized. (BE_TIMELINE_VU.md Day 19 Review; BSOT §§5.7–5.9)
- [ ] Paging defaults to `page=1`, `pageSize=20` (maximum 100). Sort defaults to `createdAt desc`, permits only `createdAt`, `departureAt`, `bookingCode`, `status`, and `totalAmount`, and adds `id` as a stable tie-breaker in the same direction. Invalid sort returns `400 INVALID_SORT_FIELD`; invalid filters/paging return `422 VALIDATION_ERROR`. (BSOT §§5.7–5.9; confirmed Q4)
- [ ] Paging past the final page returns HTTP 200 with an empty `items` array and correct seven-field `PagedResult<T>` metadata. (BE_TIMELINE_VU.md Day 19 Review; BSOT §5.7)
- [ ] `GET /v1/operator/bookings/{id}` returns the confirmed lean detail projection and append-only status timeline only when the booking belongs to the caller's operator; unknown id returns `404 BOOKING_NOT_FOUND`, while an existing foreign-operator id returns `403 FORBIDDEN` without returning foreign row data. - [ ] Both endpoints allow `OPERATOR_ADMIN` and `OPERATOR_STAFF`, return no Identity/passenger PII beyond `buyerUserId`, and never echo the searched phone. (technical context §5.1; confirmed Q3/Q5/Q7)
- [ ] Phone lookup maps only Identity 404 `RESOURCE_NOT_FOUND` to an HTTP-200 empty page; caller cancellation propagates, and all other Identity/downstream failures become FE-facing `502 UPSTREAM_UNAVAILABLE` without being misreported as caller authorization or no-match. ## Contract changes
The Day-19 REST contract is **missing** from `VietRide_API_Contract_v1.md` (repository discovery: no `/v1/operator/bookings` section). Task 19.0 must record the following human-confirmed decisions before feature workers run:

- `GET /v1/operator/bookings`: dedicated filters are `status` (one value or CSV), `tripId` (UUID), `date` (`YYYY-MM-DD`), `passengerPhone`, and `bookingCode`; do not expose `search/searchIn`. `date` filters `trip_snapshot_departure` by the `Asia/Ho_Chi_Minh` calendar day using a UTC half-open interval `[local 00:00, next local 00:00)`. `bookingCode` is trimmed exact case-insensitive. `passengerPhone` uses the existing `PhoneNumber.Normalize`: trim outer whitespace only, accept local `0...` or canonical E.164 `+84...`, canonicalize local to E.164, and reject internal separators (including spaces, hyphens, or parentheses) rather than stripping them. Paging defaults to 1/20 and caps pageSize at 100. Sort defaults to `createdAt desc`; allow-list is `createdAt`, `departureAt`, `bookingCode`, `status`, `totalAmount`, with an `id` tie-breaker in the same direction.
- List item fields are exactly `id`, `bookingCode`, `tripId`, `status`, `trip { routeName, originName, destinationName, departureAt }`, `seatCount`, `totalAmount`, and `createdAt`. The response uses ADR 0004 plus the seven-field `PagedResult<T>`.
- `GET /v1/operator/bookings/{id}` adds `buyerUserId`, `baseFare`, `discountAmount`, `totalAmount`, pickup/dropoff station/stop IDs, `bookingGroupId`, `tripDirection`, `cancellationReason`, `seats[] { passengerRecordId, ticketId, ticketCode, seatNumber, ticketStatus, boardingStatus }`, and `statusTimeline[] { status, occurredAt, reasonCode }`. It returns no phone, email, displayName, ID number, timeline actorUserId, or timeline source.
- Unknown detail id is `404 BOOKING_NOT_FOUND`; an existing foreign-operator id is `403 FORBIDDEN`. Invalid sort is `400 INVALID_SORT_FIELD`; invalid filters/paging are `422 VALIDATION_ERROR`; an unknown normalized phone and a page beyond the end both return HTTP 200 with an empty paged result.
- Both routes allow `OPERATOR_ADMIN` and `OPERATOR_STAFF`. Gateway adds the more-specific `/v1/operator/bookings` prefix to Booking without colliding with Trip-owned `/v1/operator/trips` or Booking-owned `/v1/operator/booking-stats`.
- Identity adds `GET /internal/v1/users/by-phone?phone={normalizedE164}`, protected by Internal JWT and never exposed through Gateway. Booking first validates/normalizes public `passengerPhone`, URI-escapes the canonical E.164 query value, and calls this endpoint only when the filter is present. Identity success is HTTP 200 raw `{ "userId": "uuid" }` (not ADR-0004 wrapped); no match is HTTP 404 standardized internal error envelope with existing `RESOURCE_NOT_FOUND`. Booking maps only that 404 to no user and returns the normal HTTP-200 empty seven-field paged result. Caller cancellation propagates unchanged. Identity 401/403, unexpected 4xx, 5xx, timeout/circuit-open/transport/deserialization failures map to FE-facing HTTP 502 `UPSTREAM_UNAVAILABLE` in an ADR-0004 error; they must never become caller auth failures or empty results. Retry only transient 5xx/network failures per BSOT §7.6, never 4xx. No phone snapshot or PII duplication is authorized.
- Booking adds append-only `booking_status_history`: `id uuid` PK; `booking_id uuid` local FK with `ON DELETE RESTRICT`; `status booking_status`; `occurred_at timestamptz`; nullable machine-readable `reason_code varchar(100)`; nullable `actor_user_id uuid` logical Identity FK with no DB FK; and required application-controlled `source varchar(100)`; index `(booking_id, occurred_at, id)`. Each handler captures one `IClock.UtcNow` and reuses it for the transition/creation history record—never DB read time or Outbox publish time. Sources are exactly `CREATE_BOOKING`, `CREATE_ROUND_TRIP_BOOKING`, `CONFIRM_ON_PAYMENT`, `EXPIRE_ON_PAYMENT`, `CANCEL_BOOKING`, and `MARK_REFUNDED` for the selected current writers. Create/round-trip create and passenger cancel store the authenticated passenger user id as actor; payment/system/event-driven confirm, expiry, and refund store null. `CANCEL_BOOKING` stores the existing `BookingCancellationReason` enum name as reason; all other selected writers store null. Future writers require a reviewed SOT source constant and may use only a canonical domain reason code; authenticated-human transitions store caller id, automated transitions null. Creation appends `PENDING_PAYMENT`; every successful transition appends atomically in the same local transaction. History exposes insert/read only, Booking remains non-deletable, and no update/delete API, fabricated historical backfill, or new integration event is authorized. Timeline order is `occurred_at ASC, id ASC`.
