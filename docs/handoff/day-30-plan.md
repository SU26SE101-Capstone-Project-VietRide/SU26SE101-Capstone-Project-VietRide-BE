## Objective

Deliver a reproducible Sprint-4 demonstration in which an operator creates a recurring DriverSchedule, the Trip service generates the Trip, assigned crew run that same Trip, and a Parcel moves through load, in-transit, arrival, unload, and Trip completion. Add the reviewer-facing requests to the single cumulative Postman collection without changing any REST, event, schema, error, or Gateway contract. Record the exact demo command and any observed carry-over in a Sprint-5 preparation section. This closes Sprint 4 and provides a bounded handoff into Day 31.

## Success criteria (DoD — binary, verifiable)

- [ ] The cumulative Postman collection contains an importable Day-30 folder for DriverSchedule create, Parcel load, Trip start, TripStop arrival, Parcel unload, and Trip complete through Gateway `:3000`, with correct bearer roles and UUID-v4 `Idempotency-Key` usage.
- [ ] `npm run e2e:day30` exits zero on a healthy local stack and proves that the Trip used by the lifecycle was generated from the operator-created DriverSchedule (`source=AUTO_FROM_SCHEDULE` and matching `driver_schedule_id`), not inserted directly as a Trip fixture.
- [ ] The same generated Trip reaches `BOARDING → IN_PROGRESS → COMPLETED`; its Parcel reaches `PENDING → LOADED → IN_TRANSIT → UNLOADED`, and the required Outbox/event and cargo-state evidence is correlated before cleanup.
- [ ] The runner creates only isolated generated-ID fixtures, generates short-lived JWTs and UUID-v4 keys at runtime, discloses the test-only time-advance boundary, and proves cleanup after both a normal run and an injected failure.
- [ ] `docs/handoff/sprint-4-demo-script.md` gives the exact reviewer command, expected evidence, demo narration, fixture boundary, and a Sprint-5 prep/spillover section; a green run records no known spillover explicitly, while any failure is recorded with evidence, owner, and next action rather than an invented fix.
